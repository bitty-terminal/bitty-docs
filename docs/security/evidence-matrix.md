## Evidence tiers and status vocabulary

| Tier         | Meaning per RFC taxonomy                                                                                                                          |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unit         | Boundary, allowlist, deny-list, or schema property asserted inside one crate or module                                                            |
| Integration  | Cross-component property: end-to-end enforcement, persistence across restart, or a live consumer path                                             |
| Adversarial  | Malformed, oversized, fuzz, timeout, scope-escalation, tamper, or boundary corpus that must fail closed with zero panics, hangs, or partial state |
| CI gate      | Fail-closed hygiene on every run: quality gates, `cargo deny`, `cargo audit`, CodeQL, actionlint, lint/format, and safe-mode checks where cited   |
| Manual audit | Independent reviewer-signed artifact that checks control prose against the implementation surface; required for the criteria named in the RFC     |

Cell status tokens:

| Token      | Meaning                                                                                                                                  |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `recorded` | A merged artifact records a green run or a reviewer verdict at the cited revision                                                        |
| `presence` | The artifact exists at the cited revision, but no recorded run at that revision was found in the cited evidence; closure needs a run log |
| `stale`    | A recorded run or verdict exists, but a mechanism replacement invalidates its coverage of the shipped code                               |
| `absent`   | No artifact exists for the tier; the gap column names the follow-up                                                                      |
| `n/a`      | The tier is not part of the criterion's declared verification method                                                                     |

Revision notation: a bare SHA is in the repository named immediately before
it; `@` pins the artifact. `bitty-ipc` evidence is cited at `9493674`, the
exact revision `bitty` `27807ef0` consumes; that revision is also the IPC
repository's current `main`, so pin and head agree. Audit links resolve to the
canonical `bitty-terminal-docs` copy under `security/audits/`; the authoring
revision named in each cell is the `bitty` revision the auditor reviewed.

## Review gates and lifecycle

Per [risk evidence RFC](https://github.com/bitty-terminal/bitty-terminal-docs/blob/main/specifications/risk-evidence-rfc.md)
RS-1..RS-7:

- `Open -> Mitigated` requires, for the risk's linked P0-AC set, all
  unit/integration green with recorded runs, adversarial corpus zero
  crashes/hangs, negative/limit coverage exhaustive, budget/attribution
  enforcement observable, `just check` and `ci-gate` green, secret/scope
  assertions where cited, manual-audit report where cited, and safe-mode
  re-verified where intersecting R-009/R-007/R-015/R-022.
- `Mitigated -> Accepted` adds a time-bounded CarryCtx decision with owner,
  rationale, expiry, and residual-risk follow-up; it never weakens a normative
  control. No risk is `Accepted` at this revision.
- `Reopening` occurs without a new decision on any regression in a linked
  suite, new fuzz finding, advisory, or mechanism change invalidating the
  cited hash or run. R-006/R-007 are reopened on that rule.
- This Phase E matrix stays `Open` for 18 risks; `R-001`, `R-002`, `R-003`,
  and `R-005` are `Mitigated`. `R-001`/`R-002` moved on merged auditor
  artifacts (`vt-parser-2026-09.md`, `rich-image-2026-09.md`) recorded by
  CTX-1050; `R-003` moved on `resource-loader-2026-09.md` in this revision;
  `R-005` moved at `bitty` `d4d75e9` (`5bdcdbd`, Issue #137) per PR #144
  review.
- The 2026-09-07 FIND-0002 remediation wave (`ec95c5c..0cb244d`, head
  `1fc6294`) adds `Implemented`-only rows and moves nothing on its own; each
  wave row stays `Implemented`-only pending auditor review.
- Presence of `bitty-vt`, `bitty-rich` `ImageStore`, `bitty-ipc` 256 KiB
  framing with peer credentials, or Phodopus budget code at `27807ef0` is
  `Implemented` evidence, not `Verified` closure. Where a mechanism moved, the
  ledger records `stale` rather than carrying the old verdict forward.
- `R-004` remains `Open` at `bitty` `7a4ee41` per the 2026-08-31 clipboard
  audit, which explicitly does not authorize `Open -> Mitigated` due to
  residual platform-backend, real-window UX, and `8192`-byte bound-scope gaps.
